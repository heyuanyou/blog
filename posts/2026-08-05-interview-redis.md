# Redis 高频面试题

这篇文章按面试问答形式整理，重点是表达口径准确，尽量做到能直接用于现场回答。

---

## 1. Redis 是什么？一般怎么介绍？

### Q: Redis 是什么？
**面试口径：**

Redis 是一个**基于内存的键值型 NoSQL 数据库**，同时也经常被用作**缓存**、**分布式协调组件**和**轻量消息能力组件**。

一句话介绍可以说：

> Redis 最大的特点是读写快、数据结构丰富，适合做高性能缓存和一些轻量级实时数据场景。

### Q: Redis 适合哪些场景？
常见场景有：

1. **缓存**，比如商品详情、用户信息、热点配置
2. **计数器**，比如点赞数、阅读量、库存预扣
3. **排行榜**，比如积分榜、热度榜
4. **分布式锁**，比如防止重复提交、任务互斥
5. **会话和状态存储**，比如登录态、验证码

### Q: Redis 不适合什么场景？
如果数据量远超内存预算、要求强事务关系、复杂多表查询很多，Redis 就不是首选。  
它更适合做高性能 KV 访问，不适合替代关系型数据库的核心事务场景。

---

## 2. Redis 为什么这么快？

### Q: Redis 为什么快？
**标准回答：**

1. **基于内存**，避免了磁盘 I/O
2. **核心命令执行是单线程模型**，避免了锁竞争和线程切换
3. **I/O 多路复用**，网络模型高效
4. **数据结构设计高效**，很多操作时间复杂度低
5. **通信协议和实现都比较轻量**

### Q: Redis 是不是单线程？
这个问题要答严谨。

**面试口径：**

Redis 的**命令执行主流程**是单线程的，但这不等于 Redis 整个进程所有工作都只有一个线程。  
从 Redis 6 开始，网络 I/O 读写可以用多线程辅助处理，但**命令执行本身仍然是单线程串行执行**。

### Q: 为什么单线程还能快？
因为 Redis 的瓶颈很多时候不在 CPU，而在内存访问和网络 I/O。  
单线程把锁竞争、上下文切换这些额外成本省掉了，配合内存操作，整体吞吐反而很高。

## 3. Redis 常见数据结构有哪些？

### Q: Redis 常见数据类型有哪些？
面试里通常先答这五个核心类型：

1. **String**
2. **Hash**
3. **List**
4. **Set**
5. **Sorted Set**

如果面试官继续追问，再补：

1. **Bitmap**
2. **HyperLogLog**
3. **Geo**
4. **Stream**

### Q: String 适合什么场景？
String 是最常用的类型，适合：

1. 普通缓存
2. 计数器
3. 分布式锁
4. 存 JSON 串或序列化对象

### Q: Hash 适合什么场景？
适合存对象的多个字段，比如用户信息、商品属性。  
相比把整个对象序列化成一个 String，Hash 在按字段读写时更灵活。

### Q: List、Set、ZSet 分别常见在哪些场景？
**标准回答：**

1. **List**：消息队列、最新记录列表
2. **Set**：去重、共同关注、标签集合
3. **ZSet**：排行榜、延迟任务、按分数排序的数据

---

## 4. Redis 的底层数据结构你怎么答？

### Q: Redis 的底层数据结构有哪些？
常见可以答这些：

1. **SDS**，主要用于字符串
2. **哈希表**
3. **双端链表 / quicklist**
4. **跳表**
5. **整数集合**
6. **压缩列表或后续替代结构**

### Q: 为什么 String 不是直接用 C 字符串？
因为 Redis 用的是 **SDS**，不是裸 `char*`。

这样做的好处是：

1. 获取长度是 `O(1)`
2. 二进制安全
3. 可以减少频繁内存重分配
4. 更适合 Redis 这种高频修改场景

### Q: 为什么 ZSet 常说底层是跳表？
因为跳表很适合做有序集合，支持：

1. 按 score 排序
2. 范围查询
3. 插入、删除、查找维持在 `O(logN)`

面试里可以补一句：

> ZSet 不是只有跳表，通常还会配合哈希表一起用，一个负责排序，一个负责快速定位成员。

## 5. Redis 的过期键是怎么删除的？

### Q: Redis 如何删除过期键？
Redis 不是一到过期时间就立刻删除，它主要结合两种方式：

1. **惰性删除**
2. **定期删除**

### Q: 惰性删除是什么？
访问某个 key 时，Redis 才检查它是否过期。  
如果已经过期，就在访问时删除。

优点是节省 CPU，缺点是过期 key 如果一直不被访问，可能继续占内存。

### Q: 定期删除是什么？
Redis 会周期性随机抽样一部分设置了过期时间的 key，检查并删除其中已过期的 key。

### Q: 为什么不用“定时删除”把每个 key 都精确删除？
因为如果给海量 key 都挂精确的定时任务，维护成本和 CPU 开销会很高，不划算。

### Q: 过期删除和内存淘汰是一回事吗？
不是。  
**过期删除**处理的是“已经过期的 key”，**内存淘汰**处理的是“内存达到上限时该淘汰谁”。

---

## 6. Redis 的内存淘汰策略有哪些？

### Q: Redis 常见内存淘汰策略怎么答？
面试里建议按两类说：

1. **不淘汰**：`noeviction`
2. **淘汰策略**：基于全体 key 或仅过期 key 做 LRU、LFU、随机或 TTL 优先淘汰

### Q: 常见的几个策略分别是什么？
高频的有：

1. `allkeys-lru`
2. `allkeys-lfu`
3. `volatile-lru`
4. `volatile-lfu`
5. `volatile-ttl`
6. `noeviction`

### Q: LRU 和 LFU 的区别是什么？
**标准回答：**

1. **LRU**：最近最少使用
2. **LFU**：最不经常使用

如果业务是明显的热点访问模型，LFU 通常对长期热点更友好；如果更关注最近访问行为，LRU 更直观。

## 7. Redis 持久化有哪些方式？

### Q: Redis 的持久化方式有哪些？
两种核心方式：

1. **RDB**
2. **AOF**

### Q: RDB 是什么？
RDB 是在某个时间点把内存数据做一次**快照**，写到磁盘文件里。

优点：

1. 文件紧凑
2. 恢复速度快
3. 适合做备份

缺点：

1. 两次快照之间如果 Redis 宕机，可能丢一段数据
2. 做快照本身会有资源开销

### Q: AOF 是什么？
AOF 是把写命令按协议追加到日志里，恢复时再重放这些命令。

优点：

1. 数据丢失窗口通常更小
2. 持久化语义更清晰

缺点：

1. 文件通常比 RDB 大
2. 恢复速度通常比 RDB 慢

### Q: RDB 和 AOF 怎么选？
**面试口径：**

1. 如果更关注恢复速度和备份，RDB 合适
2. 如果更关注数据丢失窗口，AOF 更合适
3. 线上通常会**同时开启**，用 AOF 提高数据安全性，用 RDB 辅助快速恢复和备份

### Q: AOF 的 `appendfsync` 常见配置怎么答？
常见有三种：

1. `always`
2. `everysec`
3. `no`

面试里一般回答：

> 线上最常见的是 `everysec`，它在性能和数据安全之间比较平衡，理论上最多丢失 1 秒左右的数据。

## 8. Redis 事务怎么理解？

### Q: Redis 支持事务吗？
支持，但 Redis 事务和关系型数据库事务不是一回事。

### Q: Redis 事务是怎么做的？
Redis 事务主要依赖：

1. `MULTI`
2. `EXEC`
3. `DISCARD`
4. `WATCH`

### Q: Redis 事务能保证什么？
**面试口径：**

Redis 事务本质上更像是**把一批命令打包后按顺序执行**。  
它能保证执行阶段不会被其他命令插队，但它**不提供关系型数据库那种完整的回滚能力**。

### Q: `WATCH` 的作用是什么？
`WATCH` 用来做乐观锁。  
如果事务执行前，被监视的 key 已经被别的客户端改过，那么事务提交会失败。

### Q: 为什么说 Redis 事务不能类比 MySQL 事务？
因为 Redis 事务没有数据库那种完整的隔离级别和回滚语义。  
面试里不要直接说“Redis 事务和 MySQL 一样有 ACID”。

## 9. Redis 缓存穿透、击穿、雪崩怎么答？

### Q: 什么是缓存穿透？
请求的数据在缓存里没有，在数据库里也没有，导致每次请求都打到数据库，这就是缓存穿透。

### Q: 怎么解决缓存穿透？
常见做法：

1. 缓存空值
2. 布隆过滤器
3. 接口层参数校验

### Q: 什么是缓存击穿？
某个**热点 key** 失效瞬间，大量请求同时打到数据库，这就是缓存击穿。

### Q: 怎么解决缓存击穿？
常见做法：

1. 热点 key 永不过期或逻辑过期
2. 互斥锁 / 单飞机制，只让一个线程回源
3. 提前预热热点数据

### Q: 什么是缓存雪崩？
大量 key 在同一时间集中失效，或者 Redis 整体不可用，导致大流量同时回源数据库，这就是缓存雪崩。

### Q: 怎么解决缓存雪崩？
常见做法：

1. 过期时间加随机值，避免同时失效
2. 多级缓存
3. 限流、降级、熔断
4. Redis 高可用部署

### Q: 这三个问题怎么一句话区分？
可以这么说：

> 穿透是“查不存在的数据”，击穿是“单个热点 key 失效”，雪崩是“很多 key 一起失效或者整个缓存层出问题”。

## 10. Redis 分布式锁怎么答？

### Q: Redis 可以做分布式锁吗？
可以，但要说清楚它的适用边界。  
Redis 分布式锁适合做**轻量级互斥控制**，但不是所有强一致场景都适合。

### Q: 最基本的加锁命令怎么写？
面试里可以回答：

> 用 `SET key value NX EX seconds`，`NX` 表示不存在才设置，`EX` 表示加过期时间。

### Q: 为什么一定要带过期时间？
为了防止持锁线程挂掉后，锁永远不释放。

### Q: 解锁为什么不能直接 `DEL`？
因为可能删掉别人的锁。  
正确做法通常是给锁写入一个唯一 value，释放时先校验 value，再删除，一般用 Lua 脚本保证原子性。

### Q: Redis 分布式锁有哪些风险？
常见风险：

1. 锁过期但业务没执行完
2. 主从切换时锁状态丢失
3. 业务执行时间不可控导致误释放

### Q: 面试里如何客观评价 Redis 锁？
可以这样答：

> Redis 锁适合大多数工程上的轻量互斥场景，但如果业务对一致性极其敏感，通常要谨慎评估，必要时会考虑更强一致的协调方案。

## 11. Redis 主从复制怎么理解？

### Q: Redis 为什么要做主从复制？
主要是为了：

1. 数据冗余
2. 故障恢复
3. 读扩展

### Q: Redis 主从复制是同步还是异步？
默认是**异步复制**。  
也就是说，主节点写成功返回给客户端后，再异步把数据复制给从节点。

### Q: 异步复制会带来什么问题？
如果主节点刚写完数据，还没同步到从节点就宕机了，而此时又发生主从切换，就可能丢这部分数据。

### Q: Redis 复制是全量还是增量？
两种都有。

1. 初次同步或差异太大时，通常会做**全量同步**
2. 正常运行时，更多是**增量同步**

## 12. 哨兵和集群模式分别解决什么问题？

### Q: Sentinel 是干什么的？
Sentinel 主要解决的是 Redis 主从架构下的**高可用故障转移**问题。

它负责：

1. 监控主从节点
2. 主节点故障判断
3. 自动故障转移
4. 通知客户端主节点变化

### Q: Redis Cluster 解决什么问题？
Redis Cluster 主要解决：

1. **高可用**
2. **数据分片**

### Q: Sentinel 和 Cluster 的核心区别是什么？
**面试口径：**

1. **Sentinel** 更像是“高可用方案”，本身不解决大规模分片
2. **Cluster** 同时解决“高可用 + 水平扩容”

### Q: Redis Cluster 的分片怎么理解？
Redis Cluster 把数据映射到固定数量的哈希槽上，常说是 **16384 个槽**，每个主节点负责其中一部分槽。

## 13. Redis 为什么不适合存超大 Key？

### Q: 什么是大 key？
大 key 一般指：

1. 单个 key 对应的 value 特别大
2. 某个集合类型里元素特别多

### Q: 大 key 有什么问题？
常见风险：

1. 网络传输慢
2. 操作阻塞时间长
3. 删除或序列化开销大
4. 容易造成内存倾斜

### Q: 怎么优化大 key？
常见思路：

1. 拆分 key
2. 控制单个集合大小
3. 避免一次性取全量数据
4. 定期扫描和治理热点大 key

## 14. Redis 常见线上问题怎么排查？

### Q: Redis 延迟高，一般先看什么？
一般先看四类：

1. CPU
2. 内存
3. 网络
4. 慢命令

### Q: 哪些命令容易导致阻塞？
要特别警惕这类命令：

1. 对大集合做全量遍历
2. 对大 key 做删除
3. 没有限制范围的大结果集读取
4. 一些复杂度较高且作用在大数据量上的命令

### Q: 为什么 Redis 会出现内存飙升？
常见原因：

1. 业务写入量暴涨
2. 过期策略不合理
3. 淘汰策略不合理
4. 大 key 或热点 key 问题
5. 缓存空值或缓存对象过大

### Q: 面试官追问“你怎么排查 Redis 问题”时怎么说？
建议按这个顺序答：

1. 先看现象，是慢、超时、丢数据、内存高还是连接数高
2. 再看监控，重点关注 QPS、命中率、延迟、主从同步、内存和网络
3. 再定位是业务流量问题、命令问题、key 设计问题还是架构问题
4. 最后给止血方案和长期优化方案

## 15. Redis 高频题怎么做最后总结？

### Q: 如果让我 1 分钟总结 Redis，我会怎么说？
我一般会这样答：

> Redis 是一个高性能的内存型键值数据库，常用于缓存、计数器、排行榜和分布式锁等场景。它之所以快，核心在于内存访问、单线程命令执行、高效数据结构和 I/O 多路复用。面试里高频考点主要集中在数据结构、过期删除、内存淘汰、RDB/AOF、缓存穿透击穿雪崩、主从复制、哨兵、集群和分布式锁。需要注意的是，Redis 很强，但它不是关系型数据库，也不能无脑承担所有高一致性场景。

---

如果你准备的是后端面试，Redis 高频题通常绕不开这些点：

1. 为什么快
2. 数据结构和底层实现
3. 过期删除和内存淘汰
4. RDB 和 AOF
5. 缓存三大问题
6. 分布式锁
7. 主从、哨兵、集群
8. 大 key 和线上排查

这些问题能讲清楚，Redis 面试基本就有框架了。
