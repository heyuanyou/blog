# MySQL 高频面试题

这篇文章按面试问答形式整理，尽量用“能直接说出口”的方式覆盖 MySQL 高频考点。

---

## 1. MySQL 是什么？一般怎么介绍？

### Q: MySQL 是什么？
**面试口径：**

MySQL 是一个主流的**关系型数据库管理系统**，最常见的使用方式是通过表结构来组织数据，并用 SQL 做增删改查。

一句话介绍可以说：

> MySQL 的核心优势是生态成熟、易用性高、事务能力强，适合大多数 OLTP 业务场景。

### Q: MySQL 适合什么场景？
常见是：

1. 订单、支付、账户这类事务型业务
2. 后台管理系统、用户系统、内容系统
3. 中小到中大型业务的核心存储

### Q: MySQL 不适合什么场景？
如果是超大规模全文检索、超高吞吐时序写入、纯缓存型场景，通常会配合 ES、ClickHouse、Redis 这类系统，而不是只靠 MySQL。

## 2. InnoDB 和 MyISAM 的区别怎么答？

### Q: 面试里 InnoDB 和 MyISAM 怎么回答？
建议抓几个高频维度：

1. **事务**
2. **锁粒度**
3. **崩溃恢复**
4. **索引结构**
5. **适用场景**

### Q: 核心区别是什么？
**标准回答：**

1. **InnoDB 支持事务，MyISAM 不支持**
2. **InnoDB 支持行锁，MyISAM 主要是表锁**
3. **InnoDB 支持崩溃恢复，MyISAM 较弱**
4. **InnoDB 主键索引是聚簇索引，MyISAM 不是**
5. 现在业务系统里绝大多数场景优先选 **InnoDB**

### Q: 面试里一句话怎么总结？

> 现在 MySQL 面试如果不特别说明，基本默认讨论的是 InnoDB。

---

## 3. 为什么 MySQL 索引常用 B+ 树？

### Q: 为什么不用哈希、二叉树，而用 B+ 树？
**面试口径：**

B+ 树适合数据库磁盘存储场景，因为它既能支持高效的单点查询，也能支持范围查询，而且树高低、磁盘 I/O 次数少。

### Q: 和二叉树比，优势是什么？
二叉树层数太高，数据量一大，访问路径就很深，磁盘 I/O 太多，不适合数据库场景。

### Q: 和哈希比，优势是什么？
哈希适合等值查询，但：

1. 不适合范围查询
2. 不适合排序
3. 不适合最左前缀这类复合索引能力

### Q: 为什么是 B+ 树，不是 B 树？
因为 B+ 树的非叶子节点只存 key，不存整行数据，所以一个页里能放更多 key，树更矮。  
另外，B+ 树叶子节点天然适合范围扫描。

## 4. 什么是聚簇索引和二级索引？

### Q: 什么是聚簇索引？
在 InnoDB 里，主键索引通常就是**聚簇索引**。  
它的叶子节点存的是**整行数据**。

### Q: 什么是二级索引？
二级索引的叶子节点存的不是完整行，而是**主键值**。

### Q: 为什么二级索引会回表？
因为通过二级索引先拿到的是主键值，然后还要再去聚簇索引里查整行数据，这一步就叫**回表**。

### Q: 什么是覆盖索引？
如果查询需要的列在索引里就已经齐了，不需要回表，这就叫覆盖索引。

### Q: 面试里怎么说覆盖索引的价值？

> 覆盖索引可以减少回表，通常能显著提升查询性能。

---

## 5. 最左前缀原则怎么理解？

### Q: 什么是最左前缀匹配原则？
联合索引比如 `(a, b, c)`，查询条件要尽量从最左边开始连续使用，才能更好地利用索引。

### Q: 为什么会这样？
因为联合索引底层是按字段顺序组织的。  
先确定 `a`，`b` 才有序；先确定 `a` 和 `b`，`c` 才更好利用。

### Q: `(a, b, c)` 下哪些能走索引？
常见可以这么答：

1. `where a = ?`
2. `where a = ? and b = ?`
3. `where a = ? and b = ? and c = ?`

如果跳过最左列，比如只查 `b`，通常就不能高效利用这个联合索引。

### Q: 面试里要注意什么？
不要把“不能用到完整联合索引”说成“完全不能走索引”，有些场景下优化器行为会更复杂，但面试基础口径这样答就够了。

## 6. 什么情况下索引会失效？

### Q: 常见索引失效场景有哪些？
高频的有：

1. 在索引列上做函数、计算、隐式类型转换
2. 联合索引没有遵循最左前缀
3. `like '%xxx'` 这种前导模糊查询
4. 选择性太差，优化器判断全表扫更划算
5. `or` 条件写法不当

### Q: 为什么 `select *` 不推荐？
因为它容易导致：

1. 读取不必要的列
2. 难以使用覆盖索引
3. 增加网络传输和回表成本

## 7. 事务的 ACID 怎么答？

### Q: 什么是 ACID？
**标准回答：**

1. **A - Atomicity，原子性**
2. **C - Consistency，一致性**
3. **I - Isolation，隔离性**
4. **D - Durability，持久性**

### Q: MySQL 里这几个特性怎么落地？
面试里常见口径是：

1. **原子性** 主要靠 `Undo Log`
2. **持久性** 主要靠 `Redo Log`
3. **隔离性** 主要靠锁和 `MVCC`
4. **一致性** 是最终目标，依赖前面几个能力共同保证

---

## 8. 事务隔离级别有哪些？

### Q: MySQL 常见事务隔离级别有哪些？
四个标准级别：

1. **Read Uncommitted**
2. **Read Committed**
3. **Repeatable Read**
4. **Serializable**

### Q: 分别会有什么问题？
**标准回答：**

1. **Read Uncommitted**：可能脏读
2. **Read Committed**：可能不可重复读
3. **Repeatable Read**：理论上会有幻读问题
4. **Serializable**：并发最低，代价最大

### Q: MySQL 默认是什么隔离级别？
InnoDB 默认是 **Repeatable Read**。

### Q: 面试里说幻读时要注意什么？
要说严谨一点：

> 从标准定义上，RR 仍需要面对幻读问题；但 InnoDB 通过 MVCC 和 Next-Key Lock，在很多场景下已经大幅降低甚至避免了常见幻读现象。

---

## 9. MVCC 是什么？怎么实现的？

### Q: 什么是 MVCC？
MVCC 是**多版本并发控制**。  
它的核心目标是让读写并发时，很多读操作不需要加重锁，也能读到合适的数据版本。

### Q: MVCC 主要用在哪些隔离级别？
主要用于 **Read Committed** 和 **Repeatable Read**。

### Q: 它靠什么实现？
面试里一般答这三样：

1. **隐藏字段**
2. **Undo Log**
3. **Read View**

### Q: Read View 在 RC 和 RR 下有什么区别？
**标准回答：**

1. **RC**：每次快照读都可能生成新的 Read View
2. **RR**：同一事务里的快照读通常复用第一次生成的 Read View

### Q: 为什么 RR 能做到可重复读？
因为同一事务里的多次快照读，通常看的是同一套一致性视图，所以结果更稳定。

---

## 10. MySQL 锁有哪些？

### Q: MySQL 锁怎么分类？
常见可以按两种方式答：

1. **按粒度**：表锁、行锁
2. **按性质**：共享锁、排他锁

### Q: InnoDB 行锁常见有哪些？
高频是：

1. **Record Lock**
2. **Gap Lock**
3. **Next-Key Lock**

### Q: Gap Lock 是什么？
Gap Lock 锁的是一个**间隙范围**，不一定锁住已有记录本身，主要是为了防止别的事务往这个范围插入新记录。

### Q: Next-Key Lock 是什么？
Next-Key Lock 可以理解成 **Record Lock + Gap Lock**。

### Q: 为什么 InnoDB 要引入 Gap Lock 和 Next-Key Lock？
主要是为了减少 RR 级别下的幻读问题。

---

## 11. 什么是快照读和当前读？

### Q: 快照读是什么？
普通 `select` 一般属于**快照读**，它读的是符合一致性视图的数据版本。

### Q: 当前读是什么？
像下面这些通常属于当前读：

1. `select ... for update`
2. `select ... lock in share mode`
3. `update`
4. `delete`

当前读读的是最新版本，并且可能加锁。

### Q: 面试里这题的核心点是什么？

> 快照读更多依赖 MVCC；当前读更多依赖锁。

---

## 12. Redo Log、Undo Log、Binlog 分别是什么？

### Q: Redo Log 是什么？
Redo Log 是 InnoDB 的**重做日志**，主要用来保证崩溃恢复和持久性。

### Q: Undo Log 是什么？
Undo Log 记录的是旧版本数据，主要服务于：

1. 事务回滚
2. MVCC

### Q: Binlog 是什么？
Binlog 是 MySQL Server 层的**归档日志**，主要用于：

1. 主从复制
2. 数据恢复

### Q: Redo Log 和 Binlog 的区别怎么答？
高频维度是：

1. **层级不同**：Redo Log 属于 InnoDB，Binlog 属于 Server 层
2. **内容不同**：Redo Log 更偏物理，Binlog 更偏逻辑
3. **用途不同**：Redo Log 解决崩溃恢复，Binlog 解决复制和恢复
4. **写入方式不同**：Redo Log 循环写，Binlog 追加写

---

## 13. 什么是两阶段提交？

### Q: MySQL 为什么要做两阶段提交？
因为一次事务提交时，Redo Log 和 Binlog 都要写。  
如果只写成功一个，另一个失败，就可能出现数据不一致，尤其会影响主从复制和恢复。

### Q: 两阶段提交怎么理解？
**标准回答：**

1. 先写 `Redo Log`，状态是 `prepare`
2. 再写 `Binlog`
3. 最后把 `Redo Log` 标记为 `commit`

### Q: 它的核心价值是什么？

> 保证 Redo Log 和 Binlog 的逻辑一致性。

---

## 14. 什么是 WAL？

### Q: WAL 是什么？
WAL 是 **Write-Ahead Logging**，也就是“先写日志，再写数据页”。

### Q: 为什么这样更高效？
因为直接刷数据页往往是随机 I/O，而写日志通常更接近顺序 I/O，成本更低。

### Q: 面试里一句话怎么答？

> MySQL 通过 WAL，把很多随机写优化成了顺序写，从而提升性能并兼顾持久性。

---

## 15. 慢 SQL 怎么排查和优化？

### Q: 面试官问慢 SQL 怎么排查，一般怎么说？
建议按这个顺序答：

1. 先定位具体慢 SQL
2. 再看执行计划
3. 再分析索引、扫描行数、排序、回表、临时表
4. 最后决定是改 SQL、加索引、改表结构还是改业务

### Q: `EXPLAIN` 重点看哪些字段？
高频看这些：

1. `type`
2. `key`
3. `rows`
4. `Extra`

### Q: `Extra` 里哪些信号要警惕？
常见是：

1. `Using filesort`
2. `Using temporary`
3. 没有命中预期索引

### Q: 慢 SQL 常见优化手段有哪些？
常见是：

1. 建合适的索引
2. 用联合索引和覆盖索引
3. 避免 `select *`
4. 优化分页
5. 避免大事务
6. 避免不合理 join

## 16. MySQL 主从复制原理怎么答？

### Q: 主从复制的核心流程是什么？
可以这样说：

1. 主库把数据变更写入 `Binlog`
2. 从库 I/O 线程拉取主库 `Binlog`
3. 写入从库本地 `Relay Log`
4. 从库 SQL 线程或回放线程执行这些日志

### Q: 为什么会有主从延迟？
常见原因：

1. 从库回放速度跟不上主库写入速度
2. 大事务拖慢复制
3. 从库资源不足
4. 网络延迟

### Q: 怎么优化主从延迟？
常见思路：

1. 避免大事务
2. 提升从库配置
3. 使用并行复制
4. 优化业务写入模型

## 17. 什么是死锁？怎么处理？

### Q: MySQL 为什么会死锁？
多个事务互相等待对方持有的锁，就会形成死锁。

### Q: MySQL 遇到死锁会怎样？
InnoDB 会做死锁检测，通常会主动回滚其中一个事务，让另一个继续执行。

### Q: 怎么减少死锁？
常见做法：

1. 固定访问顺序
2. 尽量缩小事务范围
3. 让索引更精准，减少锁范围
4. 避免长事务

---

## 18. MySQL 高频题最后怎么总结？

### Q: 如果让我 1 分钟总结 MySQL，我会怎么说？
我一般会这样答：

> MySQL 是一个成熟的关系型数据库，业务里通常重点讨论的是 InnoDB。面试高频点主要集中在索引、事务、MVCC、锁、Redo/Undo/Binlog、两阶段提交、慢 SQL 优化和主从复制。索引部分要能讲清楚为什么是 B+ 树、什么是聚簇索引、什么是回表和覆盖索引；事务部分要能讲清楚 ACID、隔离级别、MVCC 和 Next-Key Lock；日志部分要能讲清楚 Redo Log、Undo Log、Binlog 以及两阶段提交。把这几个点说顺，MySQL 面试基本就有主线了。

---

1. InnoDB 和 MyISAM
2. B+ 树、聚簇索引、回表、覆盖索引
3. 最左前缀和索引失效
4. ACID、隔离级别、MVCC
5. 行锁、Gap Lock、Next-Key Lock
6. Redo Log、Undo Log、Binlog、两阶段提交
7. 慢 SQL 优化
8. 主从复制和死锁

这些问题能讲清楚，MySQL 面试基本就有框架了。
