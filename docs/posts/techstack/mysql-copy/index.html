基础概念#

1. 什么是 MySQL？它有哪些特点？#

答案： MySQL 是一个开源的关系型数据库管理系统（RDBMS），使用 SQL 语言进行数据库管理。

主要特点：

  • 开源免费：遵循 GPL 协议
  • 跨平台：支持 Windows、Linux、macOS 等
  • 高性能：优化的查询引擎，支持高并发
  • 可扩展：支持主从复制、集群等
  • 多存储引擎：InnoDB、MyISAM、Memory 等
  • 丰富的功能：事务、视图、存储过程、触发器

2. MySQL 的架构是什么？#

答案： MySQL 采用分层架构：

客户端
  ↓
连接层（Connection Layer）
  ├─ 连接管理
  ├─ 身份验证
  └─ 权限检查
  ↓
服务层（Server Layer）
  ├─ SQL 接口
  ├─ 解析器（Parser）
  ├─ 优化器（Optimizer）
  ├─ 查询缓存
  └─ 执行器
  ↓
存储引擎层（Storage Engine Layer）
  ├─ InnoDB
  ├─ MyISAM
  └─ Memory
  ↓
文件系统（File System）

各层功能：

  • 连接层：管理客户端连接，处理认证和权限
  • 服务层：SQL 解析、优化、执行
  • 存储引擎层：数据存储和检索
  • 文件系统：物理存储

3. MySQL 有哪些存储引擎？如何选择？#

答案：

存储引擎事务支持外键锁粒度适用场景
InnoDB✅✅行锁事务处理、高并发
MyISAM❌❌表锁读多写少、全文索引
Memory❌❌表锁临时表、缓存
Archive❌❌行锁归档数据
CSV❌❌表锁数据导入导出

选择建议：

  • InnoDB：默认选择，支持事务和外键，适合大多数场景
  • MyISAM：读多写少，不需要事务的场景
  • Memory：临时表、缓存数据

4. MySQL 的数据类型有哪些？#

答案：

1. 整数类型

  • TINYINT：1 字节（-128 到 127）
  • SMALLINT：2 字节
  • MEDIUMINT：3 字节
  • INT：4 字节
  • BIGINT：8 字节

2. 浮点类型

  • FLOAT：单精度浮点数
  • DOUBLE：双精度浮点数
  • DECIMAL：精确小数（推荐用于金额）

3. 字符串类型

  • CHAR：固定长度（0-255）
  • VARCHAR：可变长度（0-65535）
  • TEXT：长文本
  • BLOB：二进制大对象

4. 日期时间类型

  • DATE：日期（YYYY-MM-DD）
  • TIME：时间（HH:MM:SS）
  • DATETIME：日期时间
  • TIMESTAMP：时间戳（自动更新）

5. 其他类型

  • ENUM：枚举
  • SET：集合
  • JSON：JSON 数据（MySQL 5.7+）

5. CHAR 和 VARCHAR 的区别？#

答案：

特性CHARVARCHAR
长度固定长度可变长度
存储固定分配空间按实际长度存储
效率查询效率高存储效率高
适用场景固定长度数据（如手机号）可变长度数据（如姓名）

示例：

-- CHAR：固定 10 字节，存储 "abc" 也占用 10 字节
CHAR(10)  -- "abc       "（7 个空格）

-- VARCHAR：可变长度，存储 "abc" 只占用 3 字节 + 1 字节长度标识
VARCHAR(10)  -- "abc"（3 字节）

选择建议：

  • CHAR：固定长度数据（如身份证号、手机号）
  • VARCHAR：可变长度数据（如姓名、地址）

SQL 基础#

6. SQL 语句有哪些类型？#

答案：

1. DDL（Data Definition Language）数据定义语言

  • CREATE：创建数据库、表、索引等
  • ALTER：修改表结构
  • DROP：删除数据库、表等
  • TRUNCATE：清空表数据

2. DML（Data Manipulation Language）数据操作语言

  • INSERT：插入数据
  • UPDATE：更新数据
  • DELETE：删除数据

3. DQL（Data Query Language）数据查询语言

  • SELECT：查询数据

4. DCL（Data Control Language）数据控制语言

  • GRANT：授予权限
  • REVOKE：撤销权限

5. TCL（Transaction Control Language）事务控制语言

  • COMMIT：提交事务
  • ROLLBACK：回滚事务
  • SAVEPOINT：保存点

7. JOIN 的类型有哪些？#

答案：

1. INNER JOIN（内连接）

  • 返回两个表中匹配的行
SELECT * FROM A INNER JOIN B ON A.id = B.id;

2. LEFT JOIN（左连接）

  • 返回左表所有行，右表匹配的行
SELECT * FROM A LEFT JOIN B ON A.id = B.id;

3. RIGHT JOIN（右连接）

  • 返回右表所有行，左表匹配的行
SELECT * FROM A RIGHT JOIN B ON A.id = B.id;

4. FULL OUTER JOIN（全外连接）

  • MySQL 不支持，可用 UNION 实现
SELECT * FROM A LEFT JOIN B ON A.id = B.id
UNION
SELECT * FROM A RIGHT JOIN B ON A.id = B.id;

5. CROSS JOIN（交叉连接）

  • 返回两个表的笛卡尔积
SELECT * FROM A CROSS JOIN B;

8. UNION 和 UNION ALL 的区别？#

答案：

特性UNIONUNION ALL
去重自动去重不去重
性能较慢（需要排序去重）较快
排序结果排序结果不排序

示例：

-- UNION：去重
SELECT name FROM table1
UNION
SELECT name FROM table2;

-- UNION ALL：不去重
SELECT name FROM table1
UNION ALL
SELECT name FROM table2;

选择建议：

  • 需要去重：使用 UNION
  • 不需要去重：使用 UNION ALL（性能更好）

9. 子查询有哪些类型？#

答案：

1. 标量子查询（Scalar Subquery）

  • 返回单个值
SELECT * FROM users WHERE age > (SELECT AVG(age) FROM users);

2. 行子查询（Row Subquery）

  • 返回一行多列
SELECT * FROM users WHERE (name, age) = (SELECT name, age FROM admins LIMIT 1);

3. 列子查询（Column Subquery）

  • 返回一列多行
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders);

4. 表子查询（Table Subquery）

  • 返回多行多列
SELECT * FROM (SELECT id, name FROM users WHERE age > 18) AS adults;

5. EXISTS 子查询

  • 检查是否存在
SELECT * FROM users WHERE EXISTS (SELECT 1 FROM orders WHERE orders.user_id = users.id);

10. GROUP BY 和 HAVING 的区别？#

答案：

GROUP BY：

  • 对结果集进行分组
  • 通常与聚合函数一起使用
  • 在 WHERE 之后执行

HAVING：

  • 对分组后的结果进行过滤
  • 只能用于 GROUP BY 之后
  • 可以使用聚合函数

示例：

-- 按部门分组，统计每个部门的平均工资，只显示平均工资 > 5000 的部门
SELECT department, AVG(salary) as avg_salary
FROM employees
WHERE status = 'active'  -- WHERE 过滤原始数据
GROUP BY department
HAVING AVG(salary) > 5000;  -- HAVING 过滤分组后的数据

执行顺序：

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

索引详解#

11. 什么是索引？索引的作用是什么？#

答案： 索引是数据库中用于快速查找数据的数据结构，类似于书籍的目录。

作用：

  • 加速查询：大幅提高查询速度
  • 唯一约束：唯一索引保证数据唯一性
  • 排序优化：索引可以帮助排序操作

代价：

  • 存储空间：索引需要额外的存储空间
  • 维护成本：插入、更新、删除需要维护索引
  • 创建时间：大表创建索引需要时间

12. MySQL 索引有哪些类型？#

答案：

1. 按数据结构分类

  • B+Tree 索引：默认索引类型，适合范围查询
  • Hash 索引：Memory 引擎支持，等值查询快
  • Full-Text 索引：全文索引，用于文本搜索
  • R-Tree 索引：空间索引，用于地理数据

2. 按功能分类

  • 普通索引（INDEX）：最基本的索引
  • 唯一索引（UNIQUE）：值必须唯一
  • 主键索引（PRIMARY KEY）：主键，唯一且非空
  • 全文索引（FULLTEXT）：全文搜索

3. 按字段数量分类

  • 单列索引：单个字段
  • 组合索引：多个字段

创建示例：

-- 普通索引
CREATE INDEX idx_name ON users(name);

-- 唯一索引
CREATE UNIQUE INDEX idx_email ON users(email);

-- 组合索引
CREATE INDEX idx_name_age ON users(name, age);

-- 全文索引
CREATE FULLTEXT INDEX idx_content ON articles(content);

13. B+Tree 索引的原理是什么？#

答案： B+Tree 是 MySQL InnoDB 引擎默认的索引数据结构。

B+Tree 特点：

  • 多路平衡树：每个节点可以有多个子节点
  • 所有数据在叶子节点：非叶子节点只存储索引键
  • 叶子节点有序链表：便于范围查询
  • 树高较低：减少磁盘 I/O 次数

结构示例：

         [50]
        /    \
    [20, 30]  [70, 80]
    /  |  \    /  |  \
[10][25][40] [60][75][90]

查找过程：

  1. 从根节点开始
  2. 比较键值，决定走哪个分支
  3. 重复直到叶子节点
  4. 在叶子节点中找到数据

优势：

  • 范围查询：叶子节点有序链表，范围查询高效
  • 磁盘友好：减少磁盘 I/O 次数
  • 适合大数据量：树高低，查询稳定

14. 什么是聚簇索引和非聚簇索引？#

答案：

聚簇索引（Clustered Index）：

  • 索引和数据存储在一起
  • InnoDB 的主键索引就是聚簇索引
  • 一个表只有一个聚簇索引
  • 数据按索引顺序存储

非聚簇索引（Non-Clustered Index）：

  • 索引和数据分离存储
  • 索引存储的是数据的指针
  • 一个表可以有多个非聚簇索引
  • 需要回表查询

对比：

特性聚簇索引非聚簇索引
数据存储索引和数据在一起索引和数据分离
数量一个表只有一个可以有多个
查询效率高（无需回表）较低（需要回表）
更新代价高（需要移动数据）低（只需更新索引）

InnoDB 示例：

-- 主键索引（聚簇索引）
CREATE TABLE users (
    id INT PRIMARY KEY,  -- 聚簇索引
    name VARCHAR(50),
    email VARCHAR(100),
    INDEX idx_email(email)  -- 非聚簇索引
);

15. 什么是覆盖索引？#

答案： 覆盖索引（Covering Index）是指查询所需的所有数据都在索引中，无需回表查询。

示例：

-- 表结构
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    email VARCHAR(100),
    age INT,
    INDEX idx_name_age(name, age)  -- 组合索引
);

-- 覆盖索引查询：所需字段都在索引中
SELECT name, age FROM users WHERE name = 'John';
-- 不需要回表，直接从索引获取数据

-- 非覆盖索引查询：需要回表
SELECT name, email FROM users WHERE name = 'John';
-- 需要回表获取 email 字段

优势：

  • 减少 I/O：不需要回表，减少磁盘 I/O
  • 提高性能：查询速度更快
  • 减少内存：不需要加载整行数据

设计原则：

  • 将查询中常用的字段放在索引中
  • 使用组合索引覆盖多个查询场景

16. 最左前缀原则是什么？#

答案： 最左前缀原则（Leftmost Prefix Rule）是指组合索引的使用必须从最左边的列开始，不能跳过中间的列。

示例：

-- 创建组合索引
CREATE INDEX idx_name_age_city ON users(name, age, city);

-- ✅ 可以使用索引
SELECT * FROM users WHERE name = 'John';
SELECT * FROM users WHERE name = 'John' AND age = 25;
SELECT * FROM users WHERE name = 'John' AND age = 25 AND city = 'Beijing';

-- ❌ 不能使用索引（跳过了 name）
SELECT * FROM users WHERE age = 25;
SELECT * FROM users WHERE city = 'Beijing';

-- ⚠️ 部分使用索引（只用到 name）
SELECT * FROM users WHERE name = 'John' AND city = 'Beijing';

原理：

  • 组合索引按字段顺序建立 B+Tree
  • 先按第一个字段排序，再按第二个字段排序
  • 跳过前面的字段无法利用索引

优化建议：

  • 将选择性高的字段放在前面
  • 考虑查询频率和字段顺序

17. 索引失效的情况有哪些？#

答案：

1. 使用函数或表达式

-- ❌ 索引失效
SELECT * FROM users WHERE UPPER(name) = 'JOHN';
SELECT * FROM users WHERE age + 1 = 26;

-- ✅ 可以使用索引
SELECT * FROM users WHERE name = 'JOHN';
SELECT * FROM users WHERE age = 25;

2. 类型转换

-- ❌ 索引失效（字符串转数字）
SELECT * FROM users WHERE id = '123';

-- ✅ 可以使用索引
SELECT * FROM users WHERE id = 123;

3. 前导模糊查询

-- ❌ 索引失效
SELECT * FROM users WHERE name LIKE '%John';

-- ✅ 可以使用索引
SELECT * FROM users WHERE name LIKE 'John%';

4. OR 条件

-- ❌ 索引失效（如果 age 没有索引）
SELECT * FROM users WHERE name = 'John' OR age = 25;

-- ✅ 可以使用索引
SELECT * FROM users WHERE name = 'John' AND age = 25;

5. 不等于操作

-- ❌ 索引失效
SELECT * FROM users WHERE name != 'John';
SELECT * FROM users WHERE name <> 'John';

-- ✅ 可以使用索引
SELECT * FROM users WHERE name = 'John';

6. IS NULL / IS NOT NULL

-- ❌ 索引失效（取决于数据分布）
SELECT * FROM users WHERE name IS NULL;

7. 组合索引不遵循最左前缀

-- 索引：idx_name_age
-- ❌ 索引失效
SELECT * FROM users WHERE age = 25;

18. 如何优化索引？#

答案：

1. 选择合适的字段

  • 选择性高的字段（区分度高）
  • 经常用于 WHERE、JOIN、ORDER BY 的字段
  • 避免在低选择性字段上建索引（如性别、状态）

2. 避免过多索引

  • 索引会降低写入性能
  • 维护索引需要额外开销
  • 一般建议单表索引不超过 5 个

3. 使用组合索引

  • 覆盖多个查询场景
  • 遵循最左前缀原则
  • 将选择性高的字段放在前面

4. 定期分析索引使用情况

-- 查看索引使用情况
SHOW INDEX FROM users;

-- 分析查询计划
EXPLAIN SELECT * FROM users WHERE name = 'John';

5. 删除未使用的索引

-- 删除索引
DROP INDEX idx_unused ON users;

事务与锁#

19. 什么是事务？ACID 特性是什么？#

答案： 事务（Transaction）是一组 SQL 操作的逻辑单元，要么全部成功，要么全部失败。

ACID 特性：

1. 原子性（Atomicity）

  • 事务中的所有操作要么全部成功，要么全部失败
  • 通过 undo log 实现

2. 一致性（Consistency）

  • 事务执行前后，数据库保持一致状态
  • 通过约束、触发器保证

3. 隔离性（Isolation）

  • 并发事务之间相互隔离
  • 通过锁机制实现

4. 持久性（Durability）

  • 事务提交后，数据永久保存
  • 通过 redo log 实现

示例：

START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;  -- 提交事务
-- 或
ROLLBACK;  -- 回滚事务

20. MySQL 的隔离级别有哪些？#

答案：

MySQL 支持四种隔离级别：

1. READ UNCOMMITTED（读未提交）

  • 最低隔离级别
  • 可能读到未提交的数据（脏读）
  • 性能最好，但数据不安全

2. READ COMMITTED（读已提交）

  • 只能读到已提交的数据
  • 避免脏读，但可能出现不可重复读
  • Oracle 默认级别

3. REPEATABLE READ（可重复读）

  • 同一事务中多次读取结果一致
  • 避免脏读和不可重复读，但可能出现幻读
  • MySQL InnoDB 默认级别

4. SERIALIZABLE（串行化）

  • 最高隔离级别
  • 完全隔离，避免所有并发问题
  • 性能最差

并发问题：

隔离级别脏读不可重复读幻读
READ UNCOMMITTED✅✅✅
READ COMMITTED❌✅✅
REPEATABLE READ❌❌✅
SERIALIZABLE❌❌❌

设置隔离级别：

-- 查看当前隔离级别
SELECT @@transaction_isolation;

-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

21. 什么是脏读、不可重复读、幻读？#

答案：

1. 脏读（Dirty Read）

  • 读取到未提交的数据
  • 如果事务回滚，读到的数据就是错误的

示例：

事务 A：UPDATE users SET balance = 1000 WHERE id = 1;  -- 未提交
事务 B：SELECT balance FROM users WHERE id = 1;  -- 读到 1000（脏读）
事务 A：ROLLBACK;  -- 回滚
事务 B：读到的数据是错误的

2. 不可重复读（Non-Repeatable Read）

  • 同一事务中多次读取同一数据，结果不一致
  • 由于其他事务修改了数据

示例：

事务 A：SELECT balance FROM users WHERE id = 1;  -- 读到 100
事务 B：UPDATE users SET balance = 200 WHERE id = 1; COMMIT;
事务 A：SELECT balance FROM users WHERE id = 1;  -- 读到 200（不一致）

3. 幻读（Phantom Read）

  • 同一事务中多次查询，结果集不一致
  • 由于其他事务插入了新数据

示例：

事务 A：SELECT * FROM users WHERE age > 18;  -- 返回 10 条
事务 B：INSERT INTO users VALUES (11, 'John', 20); COMMIT;
事务 A：SELECT * FROM users WHERE age > 18;  -- 返回 11 条（幻读）

InnoDB 的解决方案：

  • MVCC（多版本并发控制）：解决不可重复读
  • Next-Key Lock：解决幻读

22. MySQL 的锁有哪些类型？#

答案：

1. 按锁的粒度分类

表锁（Table Lock）：

  • 锁定整个表
  • MyISAM 默认锁类型
  • 开销小，加锁快，但并发度低

行锁（Row Lock）：

  • 锁定单行数据
  • InnoDB 默认锁类型
  • 开销大，加锁慢，但并发度高

页锁（Page Lock）：

  • 锁定一页数据
  • 介于表锁和行锁之间

2. 按锁的类型分类

共享锁（Shared Lock / S Lock）：

  • 读锁，多个事务可以同时持有
  • SELECT ... LOCK IN SHARE MODE

排他锁（Exclusive Lock / X Lock）：

  • 写锁，只有一个事务可以持有
  • SELECT ... FOR UPDATE、INSERT、UPDATE、DELETE

3. 按锁的意图分类

意向共享锁（IS Lock）：

  • 表示事务想要在表上获取共享锁

意向排他锁（IX Lock）：

  • 表示事务想要在表上获取排他锁

锁的兼容性：

SXISIX
S✅❌✅❌
X❌❌❌❌
IS✅❌✅✅
IX❌❌✅✅

23. InnoDB 的行锁是如何实现的？#

答案： InnoDB 的行锁通过索引实现，如果没有索引，会退化为表锁。

实现方式：

1. Record Lock（记录锁）

  • 锁定单行记录
  • 在索引记录上加锁

2. Gap Lock（间隙锁）

  • 锁定索引记录之间的间隙
  • 防止其他事务在间隙中插入数据
  • 解决幻读问题

3. Next-Key Lock（临键锁）

  • Record Lock + Gap Lock
  • 锁定记录和记录前的间隙
  • InnoDB 默认的行锁算法

示例：

-- 表：id (1, 3, 5, 7, 9)
-- 查询：WHERE id > 3 AND id < 7

-- Next-Key Lock 锁定：
-- (3, 5] - 记录 5 和间隙 (3, 5)
-- (5, 7) - 间隙 (5, 7)
-- 防止插入 id = 4 或 id = 6 的记录

锁的升级：

  • 如果查询没有使用索引，行锁会升级为表锁
  • 因此，WHERE 条件应该使用索引字段

24. 什么是死锁？如何避免？#

答案： 死锁（Deadlock）是指两个或多个事务相互等待对方释放锁，导致无法继续执行。

死锁示例：

事务 A：
  UPDATE users SET name = 'A' WHERE id = 1;  -- 锁定 id=1
  UPDATE users SET name = 'A' WHERE id = 2;  -- 等待 id=2 的锁

事务 B：
  UPDATE users SET name = 'B' WHERE id = 2;  -- 锁定 id=2
  UPDATE users SET name = 'B' WHERE id = 1;  -- 等待 id=1 的锁

结果：死锁！

避免死锁的方法：

1. 按相同顺序访问资源

-- ✅ 好：按 id 顺序访问
UPDATE users SET name = 'A' WHERE id = 1;
UPDATE users SET name = 'A' WHERE id = 2;

-- ❌ 差：顺序不一致可能导致死锁
UPDATE users SET name = 'A' WHERE id = 2;
UPDATE users SET name = 'A' WHERE id = 1;

2. 减少事务持有时间

  • 尽快提交事务
  • 避免在事务中执行耗时操作

3. 降低隔离级别

  • 使用较低的隔离级别（如 READ COMMITTED）
  • 减少锁的持有时间

4. 使用索引

  • 确保 WHERE 条件使用索引
  • 避免行锁升级为表锁

5. 死锁检测和处理

-- 查看死锁信息
SHOW ENGINE INNODB STATUS;

-- MySQL 会自动检测死锁并回滚一个事务

27. InnoDB 的日志文件有哪些？#

答案：

1. Redo Log（重做日志）

  • 记录事务的修改操作
  • 用于崩溃恢复
  • 文件：ib_logfile0、ib_logfile1
  • 循环写入，大小固定

2. Undo Log（回滚日志）

  • 记录事务修改前的数据
  • 用于事务回滚和 MVCC
  • 存储在系统表空间或独立表空间

3. Binlog（二进制日志）

Redo Log：

  • 保证事务的持久性
  • 崩溃后恢复未提交的事务

Undo Log：

  • 支持事务回滚
  • 实现 MVCC（多版本并发控制）

Binlog：

  • 主从复制
  • 数据恢复
  • 审计

28. MVCC 是什么？如何实现的？#

答案： MVCC（Multi-Version Concurrency Control，多版本并发控制）是 InnoDB 实现高并发的重要机制。

原理：

  • 为每行数据维护多个版本
  • 读操作读取历史版本，不阻塞写操作
  • 写操作创建新版本

实现机制：

1. 隐藏字段

  • DB_TRX_ID：事务 ID，记录创建/修改该行的事务 ID
  • DB_ROLL_PTR：回滚指针，指向 undo log 中的历史版本

2. Read View（读视图）

  • 事务开始时的快照
  • 包含：活跃事务列表、最小事务 ID、最大事务 ID

3. 版本链

  • 通过 undo log 构建版本链
  • 根据 Read View 判断可见性

判断规则：

  • 如果 DB_TRX_ID < min_trx_id：可见（已提交）
  • 如果 DB_TRX_ID > max_trx_id：不可见（未来事务）
  • 如果 min_trx_id <= DB_TRX_ID <= max_trx_id：
    • 在活跃事务列表中：不可见（未提交）
    • 不在活跃事务列表中：可见（已提交）

优势：

  • 读不阻塞写：读操作读取历史版本
  • 写不阻塞读：写操作创建新版本
  • 提高并发性能：减少锁竞争

性能优化#

29. 如何优化 SQL 查询？#

答案：

1. 使用索引

-- ✅ 使用索引
SELECT * FROM users WHERE id = 1;

-- ❌ 不使用索引
SELECT * FROM users WHERE UPPER(name) = 'JOHN';

**2. 避免 SELECT ***

-- ❌ 差：查询所有字段
SELECT * FROM users;

-- ✅ 好：只查询需要的字段
SELECT id, name FROM users;

3. 使用 LIMIT

-- ✅ 限制返回数量
SELECT * FROM users LIMIT 10;

4. 避免子查询，使用 JOIN

-- ❌ 差：子查询
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders);

-- ✅ 好：JOIN
SELECT u.* FROM users u INNER JOIN orders o ON u.id = o.user_id;

5. 使用 EXISTS 代替 IN

-- ✅ EXISTS 通常比 IN 性能好
SELECT * FROM users WHERE EXISTS (
    SELECT 1 FROM orders WHERE orders.user_id = users.id
);

6. 避免在 WHERE 子句中使用函数

-- ❌ 差：使用函数
SELECT * FROM users WHERE DATE(created_at) = '2024-01-01';

-- ✅ 好：使用范围查询
SELECT * FROM users WHERE created_at >= '2024-01-01' AND created_at < '2024-01-02';

7. 使用 UNION ALL 代替 UNION

-- ✅ UNION ALL 不去重，性能更好
SELECT name FROM table1 UNION ALL SELECT name FROM table2;

30. EXPLAIN 如何分析查询计划？#

答案： EXPLAIN 用于分析 SQL 查询的执行计划。

使用方法：

EXPLAIN SELECT * FROM users WHERE name = 'John';

关键字段：

1. type（访问类型）

  • ALL：全表扫描（最差）
  • index：全索引扫描
  • range：范围扫描
  • ref：非唯一索引扫描
  • eq_ref：唯一索引扫描
  • const：常量查询（最好）

2. key（使用的索引）

  • 显示实际使用的索引
  • NULL 表示未使用索引

3. rows（扫描行数）

  • 预估扫描的行数
  • 越小越好

4. Extra（额外信息）

  • Using index：覆盖索引
  • Using where：使用 WHERE 过滤
  • Using filesort：需要排序
  • Using temporary：使用临时表

优化示例：

-- 优化前：全表扫描
EXPLAIN SELECT * FROM users WHERE name = 'John';
-- type: ALL, rows: 10000

-- 优化后：使用索引
CREATE INDEX idx_name ON users(name);
EXPLAIN SELECT * FROM users WHERE name = 'John';
-- type: ref, key: idx_name, rows: 10

主从复制#

34. MySQL 主从复制的原理是什么？#

答案： 主从复制（Master-Slave Replication）是将主库的数据复制到从库的过程。

复制流程：

1. 主库（Master）

  • 执行 SQL 语句，记录到 Binlog
  • Binlog Dump 线程读取 Binlog，发送给从库

2. 从库（Slave）

  • I/O 线程连接主库，接收 Binlog
  • 将 Binlog 写入 Relay Log（中继日志）
  • SQL 线程读取 Relay Log，执行 SQL 语句

流程图：

主库（Master）
  ├─ 执行 SQL
  ├─ 写入 Binlog
  └─ Binlog Dump 线程
         ↓（网络传输）
从库（Slave）
  ├─ I/O 线程（接收 Binlog）
  ├─ 写入 Relay Log
  └─ SQL 线程（执行 SQL）

配置示例：

# 主库配置（my.cnf）
[mysqld]
server-id = 1
log-bin = mysql-bin
binlog-format = ROW

# 从库配置（my.cnf）
[mysqld]
server-id = 2
relay-log = mysql-relay-bin
read-only = 1

复制方式：

1. 异步复制（Asynchronous Replication）

  • 主库提交事务后立即返回
  • 不等待从库确认
  • 性能最好，但可能丢失数据

2. 半同步复制（Semi-Synchronous Replication）

  • 主库等待至少一个从库确认
  • 平衡性能和安全性
  • 需要安装插件

3. 组复制（Group Replication）

  • MySQL 5.7+ 支持
  • 多主复制，自动故障转移

35. 主从延迟的原因和解决方案？#

答案：

延迟原因：

1. 网络延迟

  • 主从库网络延迟高
  • 解决方案：使用内网，优化网络

2. 从库性能不足

  • 从库硬件配置低
  • 解决方案：提升从库配置

3. 大事务

  • 大事务执行时间长
  • 解决方案：拆分大事务

4. 从库负载高

  • 从库承担读请求
  • 解决方案：增加从库数量

5. Binlog 格式

  • Statement 格式可能延迟
  • 解决方案：使用 ROW 格式

解决方案：

1. 并行复制

slave_parallel_workers = 4

-- 关注：Seconds_Behind_Master

4. 使用 MTS（Multi-Threaded Slave）

  • MySQL 5.7+ 支持并行复制
  • 提高从库执行速度

分库分表#

36. 什么是分库分表？什么时候需要？#

答案： 分库分表是将大表拆分成多个小表，分散到多个数据库中。

分库：

  • 将数据分散到多个数据库
  • 每个数据库独立运行

分表：

  • 将大表拆分成多个小表
  • 可以分库分表结合使用

什么时候需要：

1. 数据量过大

  • 单表数据超过千万级别
  • 查询性能下降

2. 并发过高

  • 单库无法承受高并发
  • 需要分散压力

3. 存储空间不足

  • 单库存储空间有限
  • 需要分散存储

分表策略：

1. 水平分表

  • 按行拆分，表结构相同
  • 如：按用户 ID 取模分表

2. 垂直分表

  • 按列拆分，将字段分散到不同表
  • 如：将常用字段和扩展字段分开

分库分表示例：

-- 按用户 ID 分表（4 张表）
users_0  -- id % 4 = 0
users_1  -- id % 4 = 1
users_2  -- id % 4 = 2
users_3  -- id % 4 = 3

-- 查询时需要路由到对应的表
SELECT * FROM users_{id % 4} WHERE id = ?;

37. 分库分表的优缺点？#

答案：

优点：

  • 提高性能：单表数据量减少，查询更快
  • 提高并发：分散到多个库，提高并发能力
  • 扩展性好：可以水平扩展
  • 故障隔离：单个库故障不影响其他库

缺点：

  • 复杂度高：需要处理路由、跨库查询等
  • 事务问题：跨库事务难以保证
  • JOIN 困难：跨库 JOIN 性能差
  • 数据一致性：需要保证数据一致性

解决方案：

  • 使用中间件：MyCAT、ShardingSphere 等
  • 应用层路由：在应用层实现路由逻辑
  • 分布式事务：使用 Seata、TCC 等

# 备份单个数据库
mysqldump -u root -p database_name > backup.sql

# 备份所有数据库
mysqldump -u root -p --all-databases > all_backup.sql

# 备份表结构
mysqldump -u root -p --no-data database_name > schema.sql

# 备份数据
mysqldump -u root -p --no-create-info database_name > data.sql

2. 恢复数据

# 恢复数据库
mysql -u root -p database_name < backup.sql

# 恢复所有数据库
mysql -u root -p < all_backup.sql

3. 物理备份

# 使用 Percona XtraBackup
xtrabackup --backup --target-dir=/backup/
xtrabackup --prepare --target-dir=/backup/

4. 备份策略

  • 全量备份：每天一次
  • 增量备份：每小时一次
  • Binlog 备份：实时备份
  • 异地备份：防止单点故障

42. 什么是存储过程？如何使用？#

答案： 存储过程（Stored Procedure）是一组预编译的 SQL 语句，存储在数据库中。

创建存储过程：

DELIMITER //
CREATE PROCEDURE GetUserById(IN user_id INT)
BEGIN
    SELECT * FROM users WHERE id = user_id;
END //
DELIMITER ;

调用存储过程：

CALL GetUserById(1);

优点：

  • 性能好：预编译，执行效率高
  • 减少网络传输：一次调用执行多条 SQL
  • 安全性：可以控制权限

缺点：

  • 可移植性差：不同数据库语法不同
  • 调试困难：不如应用层代码容易调试
  • 版本控制困难：难以版本管理

43. 什么是触发器？如何使用？#

答案： 触发器（Trigger）是在表上定义的特殊存储过程，在特定事件发生时自动执行。

创建触发器：

-- 在插入前触发
CREATE TRIGGER before_insert_user
BEFORE INSERT ON users
FOR EACH ROW
BEGIN
    SET NEW.created_at = NOW();
END;

-- 在更新后触发
CREATE TRIGGER after_update_user
AFTER UPDATE ON users
FOR EACH ROW
BEGIN
    INSERT INTO user_logs(user_id, action, timestamp)
    VALUES (NEW.id, 'UPDATE', NOW());
END;

触发器类型：

  • BEFORE INSERT：插入前
  • AFTER INSERT：插入后
  • BEFORE UPDATE：更新前
  • AFTER UPDATE：更新后
  • BEFORE DELETE：删除前
  • AFTER DELETE：删除后

注意事项：

  • 触发器会增加数据库负担
  • 调试困难
  • 建议在应用层实现业务逻辑

44. 什么是视图？如何使用？#

答案： 视图（View）是基于查询结果的虚拟表，不存储数据。

创建视图：

-- 创建视图
CREATE VIEW user_orders AS
SELECT 
    u.id,
    u.name,
    COUNT(o.id) as order_count,
    SUM(o.amount) as total_amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name;

-- 使用视图
SELECT * FROM user_orders WHERE order_count > 5;

优点：

  • 简化查询：封装复杂查询
  • 安全性：可以隐藏敏感字段
  • 一致性：统一数据访问接口

缺点：

  • 性能：视图查询可能较慢
  • 限制：某些操作不支持（如某些 JOIN）

45. MySQL 的字符集和排序规则是什么？#

答案：

字符集（Character Set）：

  • 定义字符的编码方式
  • 常用字符集：utf8、utf8mb4、latin1

排序规则（Collation）：

  • 定义字符的排序和比较规则
  • 常用排序规则：utf8mb4_general_ci、utf8mb4_unicode_ci

utf8 vs utf8mb4：

  • utf8：最多 3 字节，不支持 emoji（如 😀）
  • utf8mb4：最多 4 字节，支持 emoji（推荐）

设置字符集：

-- 数据库级别
CREATE DATABASE db_name CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 表级别
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(50) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci
) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 字段级别
ALTER TABLE users MODIFY name VARCHAR(50) CHARACTER SET utf8mb4;

选择建议：

  • 使用 utf8mb4 字符集
  • 使用 utf8mb4_unicode_ci 排序规则（更准确）
